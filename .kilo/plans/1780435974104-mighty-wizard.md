# План: Исправление Reproducible Build для F-Droid

## Диагноз

Содержимое файлов внутри APK **идентично** (все 6 файлов совпадают побайтово по SHA256).

Но **ZIP-структура отличается** — и это ломает APK Signature Scheme v3:

Ошибка F-Droid: `APK Signature Scheme v3: CHUNKED_SHA256 digest mismatch`

### Детальное сравнение ZIP-структур

Анализ local file header (LFH) extras и central directory (CD) extras:

| Файл | GitHub LFH extra | GitHub CD extra | F-Droid LFH extra | F-Droid CD extra |
|------|-----------------|-----------------|-------------------|------------------|
| classes.dex | `0xD935 size=3` (7 байт) | raw zeros (3 байта) | raw zeros (3 байта) | raw zeros (3 байта) |
| libcrocson.so | `0xD935 size=3933` (3937 байт) | raw zeros (3957 байт) | raw zeros (3957 байт) | raw zeros (3957 байт) |
| classes2.dex | `0xD935 size=2` (6 байт) | raw zeros (2 байта) | raw zeros (2 байта) | raw zeros (2 байта) |
| icon.png | `0xD935 size=4` (8 байт) | нет (0 байт) | нет (0 байт) | нет (0 байт) |
| resources.arsc | `0xD935 size=3` (7 байт) | raw zeros (3 байта) | raw zeros (3 байта) | raw zeros (3 байта) |
| AndroidManifest.xml | `0xD935 size=3` (7 байт) | raw zeros (3 байта) | raw zeros (3 байта) | raw zeros (3 байта) |

Ключевое наблюдение: **apksigner 36.0.0 переписывает ТОЛЬКО LFH extras** (заменяет raw zeros → 0xD935), но **сохраняет CD extras как есть** (raw zeros из оригинального fyne output).

Также **libcrocson.so** выравнивание:
- GitHub: data@16384 → 16384 % 16384 = 0 (page-aligned)
- F-Droid: data@16400 → 16400 % 16384 = 16 (НЕ page-aligned!)

### Формат 0xD935 (zipalign extra field)

Расшифрован точный формат из GitHub APK:
```
struct zipalign_extra {
    uint16_t id;       // 0xD935 (LE: 35 D9)
    uint16_t data_size; // extra_len - 4
    uint16_t align;    // значение выравнивания: 0x0004=4 или 0x4000=16384
    uint8_t  padding[];// нулевые байты до data_size
};
```

Примеры из GitHub APK:
- classes.dex (7 байт): `35 D9 03 00 04 00 00` → id=0xD935, size=3, align=4 + 1 zero
- libcrocson.so (3937 байт): `35 D9 5D 0F 00 40 00 00...` → id=0xD935, size=3933, align=16384 + 3931 zeros
- classes2.dex (6 байт): `35 D9 02 00 04 00` → id=0xD935, size=2, align=4
- icon.png (8 байт): id=0xD935, size=4, align=4 + 2 zeros

### Алгоритм apksigner для расчёта extra

Apksigner гарантирует два условия:
1. `extra >= 6` (минимум для заголовка 0xD935 4 байта + значение выравнивания uint16 2 байта)
2. `(offset + 30 + fname_len + extra) % alignment == 0`

Алгоритм:
```python
extra = (alignment - start % alignment) % alignment
while extra < 6:
    extra += alignment
```

Проверка на всех файлах GitHub APK — все совпадают.

## Причина

**Версии fyne tools совпадают** (`dc72a0f` = HEAD `main`). Fyne writer (`writer.go:137`) создаёт extra fields как `make([]byte, extra)` — сырые нули.

**Полная цепочка сборки:**

### GitHub (`fyne.yml`):
1. `fyne package -os android/arm --release` → APK с raw-zero extras (LFH и CD)
2. `apksigner sign` (build-tools 36.0.0) → переписывает ZIP:
   - LFH: raw zeros → 0xD935 (пересчитывает выравнивание, мин. 6 байт)
   - CD: сохраняет оригинальные raw-zero extras (без изменений!)
   - Добавляет APK Signing Block между данными и CD

### F-Droid (`com.github.abakum.crocson.yml`):
1. `sdkmanager "build-tools;36.0.0"` — ставит build-tools 36.0.0
2. `fyne package -os android/arm --release` → APK с raw-zero extras
3. **Нет apksigner** — F-Droid подписывает серверно своей инфраструктурой
4. Результат: LFH extras = raw zeros (отличаются от GitHub)

**Историческая причина поломки:**
- **v1.11.60**: рецепт содержал `zip -d META-INF/*` + `zipalign -f -p 4` → 0xD935 extras совпадали
- **v1.11.61** (коммит `16758c7`): `zip -d` и `zipalign` убраны → fyne создаёт нули

## Критическая проблема: Вариант B (writer.go) НЕ работает для существующего v1.11.61

Подробный анализ показал, что простой фикс writer.go **не решит проблему**:

1. **CD extras**: Go `archive/zip` пишет ОДИНАКОВЫЕ extras для LFH и CD. Но apksigner 36.0.0 пишет РАЗНЫЕ extras (0xD935 в LFH, raw zeros в CD). Нельзя воспроизвести это через стандартный Go zip library, т.к. `CreateHeader` делает копию `FileHeader` — изменение после вызова не влияет на CD.

2. **Разные размеры extras**: 0xD935 формат требует extra >= 6, а fyne с raw zeros — минимум 0. Это меняет размеры padding → смещаются все последующие записи → меняется всё.

3. **Существующий релиз v1.11.61**: GitHub APK уже выпущен. Нельзя ретроактивно его пересобрать. Любое изменение fyne даст ДРУГОЙ APK (даже если align вычисления совпадут для LFH, CD extras будут отличаться).

## Решение: Вариант A — Добавить apksigner в F-Droid рецепт

Единственный способ получить **идентичный** ZIP для v1.11.61 — повторить ТОТ ЖЕ процесс сборки GitHub:

```
fyne package (raw zeros) → apksigner 36.0.0 (0xD935 LFH + raw-zero CD + signing block)
```

### Вариант A1: apksigner с debug key

Добавить в `com.github.abakum.crocson.yml`:

```yaml
build:
  - ...
  - fyne package -os android/arm --release
  - keytool -genkeypair -keystore /tmp/debug.keystore -alias CROC -storepass android -keypass android -keyalg RSA -keysize 2048 -validity 1 -dname "CN=gomobile"
  - $$SDK$$/build-tools/36.0.0/apksigner sign --ks /tmp/debug.keystore --ks-key-alias CROC --ks-pass pass:android --key-pass pass:android crocson.apk
  - rm /tmp/debug.keystore
```

**Проблема**: apksigner добавит META-INF/{alias}.{SF,RSA} — имя alias'а и содержимое (хэши, подпись) попадут в v3 digest. Это не совпадёт с GitHub APK (там ключ разработчика, alias "CROC" или подобный).

### Вариант A2: zipalign (проверенный подход)

Добавить `zipalign` в рецепт. Работало для v1.11.60.

```yaml
build:
  - ...
  - fyne package -os android/arm --release
  - $$SDK$$/build-tools/36.0.0/zipalign -f -p 4 crocson.apk crocson-aligned.apk
  - mv crocson-aligned.apk crocson.apk
```

**Проблема**: zipalign пишет 0xD935 в ОБА (LFH и CD), а apksigner 36.0.0 пишет 0xD935 только в LFH (CD остаётся raw zeros). CD extras будут отличаться:
- GitHub: CD extra = raw zeros (сохранено apksigner из fyne output)
- F-Droid: CD extra = 0xD935 (от zipalign)

**НО**: нужно проверить — F-Droid-ный apksigner (при серверном подписывании) перезапишет ли CD extras. Если да, то zipalign может не помочь.

### Вариант A3: zipalign + apksigner (полная имитация GitHub процесса)

Имитировать точный процесс GitHub: fyne → zipalign → apksigner. Но это требует ключа разработчика, которого нет у F-Droid.

### Вариант B2: Исправить writer.go + перевыпустить релиз

1. Изменить `writer.go` — писать 0xD935 для LFH и raw zeros для CD
2. Это потребует post-processing (Go zip library не разделяет LFH/CD extras) или патч самого zip.Writer
3. Пересобрать и перевыпустить v1.11.61 (или выпустить v1.11.62)
4. Обновить srclib в F-Droid

Плюсы: работает для всех будущих релизов, не нужен zipalign/apksigner в рецепте
Минусы: сложная реализация (post-processing ZIP), нужно перевыпускать

### Вариант C: Передать fyne tool флаг `--sign` (самый простой)

Fyne tool уже умеет подписывать через `apksigner` (`signAPK()` в `build_androidapp.go:689`). Флаг `--sign` в `build_androidapp.go:183` контролирует это:

```go
apkw, err := buildAPK(out, nmpkgs, libFiles, androidArchs, !buildReleaseFlag && !buildSign, activityDex)
```

При `--sign`:
- `sign = true` → fyne создаёт META-INF (с debug ключом из hardcoded `debugCert`)
- затем вызывает `signAPK()` → находит `apksigner` в PATH → подписывает

F-Droid рецепт мог бы добавить `--sign` к `fyne package`:
```yaml
- fyne package -os android/arm --release --sign
```

Но это тоже подпишет debug ключом → META-INF будут отличаться.

## Что ещё нужно выяснить

1. **Как F-Droid подписывает APK**: использует ли apksigner? Какую версию? Переписывает ли LFH extras?
2. **Какой alias у ключа в GitHub workflow**: META-INF/CROC.SF и CROC.RSA → alias = "CROC"
3. **Содержимое MANIFEST.MF**: если fyne подписывает (sign=true), хэши в MANIFEST.MF зависят от SHA1 каждого файла. Файлы идентичны, но порядок записей может отличаться
4. **Тест zipalign**: что именно zipalign делает с CD extras — переписывает или сохраняет
